# v2.0.4 — 按执行能力调整 GPT 指挥深度

- 日期：2026-09-04
- 版本：2.0.4

## 改了什么

1. 将 `planning_policy.mjs` 规则升级为 v2，取消文件数、步骤数、交付物数的限制，保留按需求拆任务及 ID/依赖校验。模型/推理档位改为映射到逐步指挥、详细指导、关键点指导、模块委托、目标委托五种协作方式。
2. Flash Off 需要 GPT 先明确方案、输入/接口、具体文件、实现说明、逐步动作及预期、边界情况、验证与失败处理，再派发小任务。其他档位逐步减少 GPT 必填细节；Pro Max 可以只收到目标、范围、交付物、依赖和验收，由 DeepSeek 自主设计与实现。
3. 编排器在任务信封中写入 `execution_guidance`，执行者首轮与续轮均按该字段确定自主空间。规划提示、解析、派发前检查使用同一套规则。真实模型比预期弱时，指导不足的任务仍会被拒绝。
4. 逐步/详细/关键点指导增加逐任务 GPT 检查，提交原指令、报告和本地验证证据，确认后才继续。`pending_task_review` 持久化等待状态，`task_reviews` 保存检查记录并进入审计导出。错误 DONE 不能跳过剩余任务；检查期间暂停和恢复仍保留派发边界。全部任务之后仍生成项目分析并进行整体验收。
5. 逐步/详细指导首次失败回滚后直接交回 GPT，携带错误、原指令和可用执行报告，要求修改方案、补说明或继续拆小，不原样自动重试；修订前不接受 CONTINUE/DONE。较高自主档仍保留执行者重试路径。
6. 升档重规划时，新任务完整替换旧任务契约，省略的细节不会被旧步骤重新填回；已完成任务的记录仍保留。
7. 更新 README、Mock 计划及回归测试，不增加依赖，不改变 GPT 浏览器的单页启动修复。

## 为什么

用户希望由 GPT 为弱模型承担更多设计、分解和纠错工作，让其获得足够清楚的执行指令；强模型则应拥有更大的自主发挥空间。原 v1 规则限制了数量，却对各档位都要求详细步骤，没有准确表达这种分工。本次把规则的重点改成指挥深度，并将监督和失败反馈接入实际状态机。

目标是提高整个协作系统的任务完成能力，不宣称改变模型本身或已经证明 Flash Off 等同 Pro Max。更详细指挥会增加 GPT 往返与耗时；实际收益需通过相同任务和相同验收标准下的成功率、返工、时间及成本对比确认。

## 验证

- `npm test`：核心/指挥规则回归、协议、GPT Mock、文件夹选择器通过。
- 覆盖所有档位映射、长指令不受数量限制、强档最小委托、低档指导不足拒绝、降档补细节、升档移除旧步骤、逐任务检查门槛、恢复不重复发送、误判 DONE 限制、弱档失败回 GPT、强档自主重试及暂停竞态。
- 完整 Mock 协作闭环包含三次 GPT 逐任务检查与最终验收。
- 未进行真实模型质量/成本对比，因此不把测试通过视为模型能力等同的证明。
- 未修改 Dashboard 界面，无需 UI 回归；未编辑既有项目、浏览器登录态或运行日志。
